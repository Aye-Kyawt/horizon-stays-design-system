gitignored and generated by `AIRTABLE_PAT=pat... npm run registry:init`; no `AIRTABLE_PAT` is
available on this machine.

`.claude/skills/registry/SKILL.md` is unambiguous about what to do:

> If the local file is missing, stop and say so. Do not guess an ID, do not read one out of a
> browser URL, and do not paste one into a skill, an agent file, or a script.

So **`Release Review` and `Release Verdict` were not written for either component.** The skill
also forbids writing one without the other, so a partial record was never an option either.

What this review *did* do, and the distinction matters: for the **reads** that G2 and G6 depend on,
table and field IDs were resolved **live**, by name, against the base itself
(`list_tables_for_base` on `appC2wElEJUDWraBG`), and the names matched the contract exactly. That
is a read path, it hardcodes nothing, and it is if anything more current than the cached file.
Nothing was written back through it, and no ID has been committed to any file in this repo.

**The remedy is one command**, after which a reviewer can write both cells in a single step:

```
AIRTABLE_PAT=pat... npm run registry:init
```

The release as a whole is **Blocked**. One finding blocks both components, and it is the same one.

**`npm test` fails at this commit — 8 failed, 37 passed.** All eight failures are the same new
assertion in
[`src/test/tokenDiscipline.test.ts`](https://github.com/Aye-Kyawt/horizon-stays-design-system/blob/3e0cf2c8ee874b3bf1c37d2d73e121034b21d6e7/src/test/tokenDiscipline.test.ts),
added on this branch in commit `3e0cf2c`: *"reads no base-layer `--core-*` token"*. It fails for
**Button, avatar, cardText, chip, iconBtn, progressBar, spinner and tooltip** — eight of the
eleven component stylesheets. Only cardContainer, cardImage and cardLayout pass it.

This is worth stating precisely, because it would be easy to read the new test as having *caused*
the failure. It did not. The `--core-*` reads were already in those stylesheets and already
violated `CLAUDE.md`; G3 would have failed both components under review on its stylesheet clause
whether or not the test existed. What the test changed is *when* the violation surfaces — the
test's own header comment says so:

> Until this check existed the gate was the only thing that caught it, which let a stylesheet reach
> `Completed` on a green test run and then block at review — the expensive end to find out.

That is exactly what happened here, for both components. The board shows them `Completed`; the
gate blocks them.

**Ranked, what has to happen before a release review can clear either component:**

1. **Replace the base-layer `--core-*` reads with semantic tokens** — 9 in `Button.css`, 7 in
   `cardText.css` (and 6 more stylesheets outside this review's scope). Owner: 🔨 Engineer. If a
   semantic token does not exist for one of them, `CLAUDE.md` is explicit that the gap is reported,
   not filled by inventing a token.
2. **Write `src/components/cardText/cardText.intent.json`.** Owner: 📚 doc-generator. It unblocks
   G1 and makes C1, C3, C4, C5 and C6 evaluable for cardText for the first time.
3. **Record a decision on the `showPrice` / `showReview` / `showMetadata` rename**, either way, in
   `docs/cardContainer-naming.md`. Owner: 🎨 Designer, since it is a design-file change. This is the
   G5 judgement call above and a reviewer may overrule it.
4. **Generate `.claude/registry.local.json`** so the verdict cells can be written.

Items 1–3 are fixes this review deliberately did not make. `.claude/skills/release-review/SKILL.md`
is explicit that a review which repaired what it found has reviewed its own work; no file under
`src/`, no intent file and no `docs/` file was edited, and nothing was published, tagged, merged or
deployed.
